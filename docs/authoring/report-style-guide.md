# 报告与设计文档写作规范

本规范定义在本仓库内**生成分析报告、设计文档、技术评估**时必须遵循的内容、结构、
引用、图表、语言与防幻觉要求。它是这一类产出的唯一权威标准；`report-authoring`
技能与根目录 `CLAUDE.md` 均指向本文件，使其在 Claude Code 中切实生效。

## 适用范围与定位

- **适用**：面向他人阅读的分析报告、设计文档、架构/部署说明、技术评估、调研结论。
- **不适用**：STORM 流水线自动生成的维基式文章（其体例由 `knowledge_storm` 内部提示
  决定）；纯代码改动与提交信息；终端里的简短交互答复。
- 当某产出既是"给人读的报告"又落盘为文档时，以本规范为准。

## 报告结构与排版规范

### 先行输出章节大纲

正文开始前，先给出本报告的**输出章节大纲**，让读者对全文的推进路径一目了然，再逐节
展开。大纲应反映论证的递进关系，而非简单罗列标题。

### 层级标题与叙述

- 使用清晰的 Markdown 层级标题（二级 `##`、三级 `###`），层次分明。
- 每一个观点都要展开说明其来由与含义，拒绝干巴罗列；用通俗、生动的语言把洞见讲透，
  让读者在阅读中逐步建立理解，而不是只看到结论。
- 避免过程性或非正式表述（例如"任务二""下一步""某某图"之类），一律用专业、流畅的
  叙述与规范术语。

### 关键对比用表格

凡涉及方案、指标、优劣、取舍的**并列对比**，一律用表格呈现；表格只承载可枚举的要点，
展开解释放在表格前后的正文里。示例：

| 维度 | 方案甲 | 方案乙 |
|---|---|---|
| 依赖 | 无需外部密钥 | 需付费 API 密钥 |
| 适用 | 快速验证 | 生产级质量 |

### 结论置后

不要开篇即给答案。应引导读者层层递进，让观点与洞察在论证末尾自然浮现；报告的最终结论
放在最后一节。

## 证据与引用规范

### 观点需现实锚点

每一个判断都必须有**现实发生的事件或可查证的数据**作为锚点，避免过度空泛的预测或推断。
无可靠来源支撑的内容，宁可不写。

### 数字引注与参考资料

- 正文中引用外部网页或资料时，使用数字引注标识，如 `[1]`。
- 文末设置"参考资料"章节，按序列出每条引注的完整名称与链接。
- 只引用真实、可访问的来源；严禁编造来源、标题、作者或链接。

### 引用自闭环（in-place 完整表达）

引注与链接只承担**核验/溯源**职责，不承担**表达**职责。硬性要求：

- **`[n]` 引注处自闭环**：当前句/段必须就地写出被引来源的关键事实、数字与结论，读者不查
  参考资料即可完整理解。反例："该特性存在性能问题 [3]"；正例："启用分层后 vMotion 需先取回
  慢层页，迁移时长为基线的 1.5–2 倍 [3]"。
- **跨文档引用同理**：写"见 X 文档"之前，须先就地概括 X 中支撑当前论点的结论要点（关键机制、
  函数、数字），链接仅供读者深挖与核验；禁止只留一个"详见 X"的跳转让读者自己拼装含义。
- **不为篇幅牺牲自闭环**：不刻意限制文档篇幅——就地把内容讲透优先于精简；宁可正文长，不可
  让理解依赖多文档跳转。

### 结论闭环（不留悬留存疑）

交付级报告**不得**在文末（或任何处）堆放"无法确定 / 待实测 / 待证 / TBD"这类悬留问题。这与防
幻觉的"不确定就答无法确定"并不矛盾：防幻觉禁止你**编造**，本条要求你**去核实并把问题推进到闭环**，
而不是停在问题上。每条存疑必须落到三种可闭环形态之一：

1. **已核验事实**——经独立检索或一手源核实成立，正常引注并就地写全。
2. **有依据的工程判断 + 可证伪门**——没有实测环境时，基于机制等价与可核验公开锚点给出**确定的
   预测结论**（显式标注为预测、非实测），并配可证伪假设 + kill-gate（阈值可待基线，门必须在）。它
   支撑决策，因此是结论而非开放问题。
3. **确定的"公开不可得"判定 + 处理**——经核实截至某日确实无法从公开/一手源确认者，给**确定判定**
   （"经核验，截至 YYYY-MM 不可确认"）+ 处理（降级为概念级、改挂可核实替代源、或从结论中剔除其
   支撑作用）。这是确定结论，不是待办。

对高价值/高风险、一次检索难以定论的项，应**启动多个独立、资深、专业的 reviewer 对拍**（配置与主
执行者一致）收敛证据，主执行者对其一手结论**再核验**后采纳。

## 图表规范

- 所有图表**一律使用 Mermaid 格式**输出，并与正文叙述紧密结合：图表前后须有文字解释其
  设计逻辑与要点，把图、设计决策与需求联系起来。
- **必备图表类型**：架构图（描述系统内部模块的层次与依赖关系）、部署图（描述组件、节点
  及其运行时关系）。
- **可选图表类型**：组件时序图（核心业务场景下模块间的交互与调用顺序）、数据流/控制流图
  （核心业务的数据流转与控制逻辑）。
- Mermaid 的具体书写规则（中文文本、全角括号、`<br>` 换行、`%%` 注释、置顶图例、专业
  配色、业务流序号等）详见附录《[Mermaid 图表详细格式规范](mermaid-style-guide.md)》，
  其中的合规示例可直接复用。

## 语言风格

- 表达要饱满、流畅、易懂；避免晦涩缩写与生僻术语，必要术语首次出现时用通俗话语解释。
- 不干巴罗列事实，而要营造阅读体验，让读者在体会与领悟中获得真正的理解。
- 保持克制，只回应主题本身，不主动堆砌无关信息。

## 防幻觉与核验强制要求

以下为硬性约束，产出前必须逐条自检并清除违规内容。

### 事实真实性

- 严禁虚构任何数据、案例、人名、地名、文献、时间、法规等信息。
- 不确定、无可靠来源或超出可查证范围的内容，直接声明"无法确定"或"不知道"，不强行作答。
- 不做无依据推断，不脑补细节，不延伸未提及的信息。
- 所有事实性内容必须来自公开可查证来源；不杜撰来源、条款、标准、论文标题与作者。
- 涉及专业领域时只陈述公认结论，并明确区分"事实"（可验证）与"个人理解"（须标注）。

### 表述克制

- 不使用"据报道""相关研究显示"等模糊来源表述；无明确来源则不提及该说法。
- 不生成不存在的文件、条款、标准、论文或统计数据。
- 禁止使用无依据的绝对化表述（如"所有""一定""从未"）。
- 不杜撰历史事件、实验结果、统计数据或百分比。

### 交付前自检

- 删除所有未经证实、无法溯源、主观臆断的内容。
- 对每条事实性陈述确认其来源可查；对每条观点确认已标注为个人理解。
- 若无法判断真伪，直接说明，不以猜测填补。

## 交付前自检清单

- [ ] 正文前已给出章节大纲，结论置于末尾。
- [ ] 层级标题清晰；对比信息以表格呈现。
- [ ] 每个判断都有现实事件或数据锚点；引注使用 `[n]` 且文末有"参考资料"。
- [ ] 每处 `[n]` 引注与跨文档链接均已 in-place 自闭环：当前文字独立可完整理解，跳转仅供核验
  与深挖；未为控制篇幅而省略就地阐述。
- [ ] 含架构图与部署图；全部图表为 Mermaid 且符合附录格式（无英文圆括号、`<br>` 换行、
  `%%` 注释独占一行、图例置顶）。
- [ ] 图表周围有文字解释，与需求和设计决策相呼应。
- [ ] 语言饱满流畅；无过程性/非正式表述。
- [ ] 已完成防幻觉自检，无虚构与无据推断。
